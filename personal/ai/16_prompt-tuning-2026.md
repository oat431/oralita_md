# Prompt Tuning (Q4 2026): The Soft Middle Between Prompting and Fine-Tuning

> **Your question:** What is "prompt tuning" actually - is it just better prompt writing, or something else - and when is it the right lever in 2026?
> **Short answer:** Prompt tuning is **not** prompt writing. It is a parameter-efficient fine-tuning (PEFT) method: keep the model's weights frozen, train a short sequence of continuous embedding vectors (a "soft prompt"), and prepend it to every input. It sits between prompt engineering (a human writes discrete text) and fine-tuning (weights change). In 2026 it has exactly one real niche left: many cheap per-task adapters over a single self-hosted frozen model. For almost everything else LoRA won, and for closed APIs it never applied at all.
> **Verification:** Web-checked 2026-11-18. The serving numbers in section 7 are one 2026 measurement on one backbone - treat them as directional, not gospel.

## 1. The name problem: three different "tunings" 🏷️

Half the confusion about this topic is people in the same meeting meaning different things. The other half is vendors who benefit from the confusion. Sort them once:

| Term | What it actually changes | Who can do it | Status |
|---|---|---|---|
| **Prompt engineering** | The text of the prompt (hard prompts, discrete tokens) | Anyone with any API | ✅ Standard |
| **Prompt optimization** (DSPy, GEPA, ...) | Also just text, but searched or generated by a tool instead of a human | Anyone with any API | 🟢 Emerging |
| **Prompt tuning** (this note) | A learned embedding vector (soft prompt) prepended at the input layer | Only where you can touch the embedding layer (self-hosted open weights) | 🟡 Niche (standard as a technique) |
| **Full fine-tuning** | Every model weight | Training access plus real compute | 🟡 Niche (mostly replaced by PEFT) |

Two clarifications worth saying out loud in any design review:

1. **"Prompt tuning" is also used loosely to mean prompt optimization** ("we tuned the prompt" = a human or a search tool rewrote text). If someone claims a win from "prompt tuning", ask whether gradients were involved. If no gradients, they mean the left column, and this note does not apply.
2. **Prompt optimization is real and often enough.** Before any training at all, HF's own guidance is: prompt the model first, and only escalate if the eval set says the ceiling is here. A tool that rewrites your text prompt beats a training run you did not need.

## 2. How a soft prompt actually works ⚙️

**Hard prompts** are text: discrete tokens like "Translate to French:" that a human writes and the tokenizer turns into embeddings. **Soft prompts** are learnable tensors of the same dimensionality as token embeddings, concatenated with the input - arbitrary floating-point vectors that no tokenizer would ever produce. "Virtual tokens" is the usual name.

The mechanism is deliberately boring:

1. Load the pretrained model with **all weights frozen**.
2. Allocate a small trainable embedding matrix, typically **10 to 100 virtual tokens**.
3. Prepend it to every input sequence. The frozen model processes it like any other embedding.
4. Run gradient descent **only on the prompt embeddings**. The whole task adaptation lives in those vectors.

A minimal Hugging Face PEFT sketch (Qwen3-8B as the frozen backbone):

```python
from peft import PromptTuningConfig, PromptTuningInit, TaskType, get_peft_model
from transformers import AutoModelForCausalLM, AutoTokenizer

# 1. Load the frozen backbone. from_pretrained gives inference weights;
#    nothing here is trainable yet.
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen3-8B")

# 2. Describe the soft prompt: length, and how to initialize it.
config = PromptTuningConfig(
    task_type=TaskType.CAUSAL_LM,
    num_virtual_tokens=20,                     # the soft prompt's length in token slots
    prompt_tuning_init=PromptTuningInit.TEXT,  # init from real words, not random noise
    prompt_tuning_init_text="Classify the sentiment of the following review:",
    tokenizer_name_or_path="Qwen/Qwen3-8B",
)

# 3. Wrap the model. After this, only the soft prompt has gradients.
model = get_peft_model(model, config)
model.print_trainable_parameters()  # sanity check: ~0.01% of params should be trainable
```

Line by line, because the failure modes hide in the details:

- `from_pretrained(...)` loads the **frozen** backbone. Prompt tuning never touches these weights again.
- `num_virtual_tokens=20` is the whole adapter. Too few and the model is under-steered; too many and you burn context positions (see below).
- `prompt_tuning_init=PromptTuningInit.TEXT` is not optional decoration. **Random initialization is the classic footgun**: the optimizer wanders into local minima or converges slowly. Initializing from the embedding of a real task description gives it a sane starting point.
- `get_peft_model(...)` wraps the model so only the prompt matrix receives gradients. `print_trainable_parameters()` is the one-line audit that proves it.

Three costs, all real:

- **Not human readable.** A soft prompt is a vector, not a sentence. You cannot read it, diff it in review, or "fix a typo" in it. Debugging a regression means evals and ablations, not editing.
- **It occupies the context window.** 20 virtual tokens means 20 fewer positions for input and output. Near the context limit this bites.
- **Training is fiddly.** A tiny parameter count concentrates gradients and oscillates. The standard recipe: learning rate 1e-4 to 5e-4 (lower than LoRA's usual), warm up over the first 5 to 10% of steps, cosine schedule.

## 3. The family: prompt tuning and its three siblings 👪

Prompt tuning (2021) spawned a small family within two years. They differ in **where** the trainable vectors sit, and that placement is the whole trade-off:

| Method | Where the trainable vectors go | Rough trainable params | Note |
|---|---|---|---|
| **Prompt tuning** (Lester et al., 2021) | Input embedding layer only | 10K to 100K | Simplest. Performance scales up with model size |
| **Prefix tuning** (Li and Liang, 2021) | Keys and values at **every** transformer layer | 1M to 5M | More expressive. Needs a reparameterization MLP or training diverges |
| **P-tuning v1** (Liu et al., 2021) | Anywhere in the input, wired together by an LSTM or MLP encoder | Small plus encoder | Aimed at NLU tasks on GPT-style models |
| **P-tuning v2** (Liu et al., 2022) | Deep prompts across all layers, no encoder | Between prompt tuning and prefix tuning | Best of the family on NLU at smaller model scales |
| **Multitask / transfer variants** (SPoT, MPT) | Same as above, but initialized or composed from other tasks' soft prompts | Same | Soft prompts transfer between related tasks |

Why placement matters: in plain prompt tuning the soft tokens can only influence the model through attention at the first layer. Prefix tuning puts the learned keys and values at every layer, so the prefix steers attention throughout the whole forward pass. More leverage, more parameters, more machinery.

## 4. The finding that made it famous: scale 📈

The headline result of the original paper (Lester et al., 2021, "The Power of Scale for Parameter-Efficient Prompt Tuning") is a scaling law:

- **Below roughly 1B parameters**, prompt tuning underperforms full fine-tuning significantly. The model is not steerable enough; the soft prompt cannot carry the task.
- **At around 10B and up** (the paper's largest was T5-XXL at 11B), prompt tuning **matches full fine-tuning** while training only the soft prompt - on the order of 0.01% of the model's parameters.
- The gap between initialization strategies shrinks as models grow. Scale forgives.

The intuition that survived: **a soft prompt does not teach the model new skills, it elicits skills that pretraining already put there.** The bigger the model, the more skills there are to elicit, and the less steering it needs.

---

## 5. What it cannot do: the theory limit 🚧

The expressiveness question got a formal answer ("When Do Prompting and Prefix-Tuning Work?", arXiv 2310.19698), and the answer is sobering:

- Soft prompting and prefix tuning are **strictly more expressive than text prompts** (continuous space beats discrete tokens), but **strictly less expressive than full fine-tuning**, even at equal parameter counts.
- Mechanically: context-based tuning **cannot change the relative attention pattern** over content. It can only bias an attention layer's output in a fixed direction (a subspace of rank equal to the prefix size).
- Translation: these methods can **elicit** a skill the pretrained model already has, and can even pick up a new task if pretraining gave it the pieces. They **cannot learn genuinely novel tasks that need new attention patterns**. Full fine-tuning can. That is the boundary, drawn in math rather than vibes.

## 6. Where prompt tuning stands in 2026 🗺️

The honest status: **LoRA took the PEFT crown years ago**, and prompt tuning survived in the corner where LoRA's specific weaknesses hurt.

- **For single-task adaptation, LoRA or QLoRA wins almost everywhere.** It adapts attention matrices throughout the network, captures more task signal at comparable parameter counts, and has mature tooling: HF PEFT, vLLM's `--enable-lora` multi-adapter serving, SGLang, Microsoft Foundry's Multi-LoRA preview. Soft-prompt methods are "largely supplanted by LoRA for most fine-tuning use cases" (2026 survey, arXiv 2610.00928).
- **Closed APIs cannot be prompt-tuned at all.** Soft prompts require embedding-layer access. `gpt-*`, `claude-*`, `gemini-*` endpoints do not give it to you. Prompt-based adaptation (text) is the only game on hosted models, which is why the frontier-API era pushed most teams away from weight-level adaptation entirely.
- **The one live niche: multi-tenant serving over one frozen model.** Many tasks or customers, each with a few hundred labeled examples, all served from a single GPU-resident base model. The per-task adapter is a vector of a few hundred KB to under 2 MB - hot-swappable at request time, no adapter kernels in the decode loop. LoRA per tenant works too, but each adapter is tens of MB and costs per-token compute when unmerged.

The verdict, up front:

| Question | Answer |
|---|---|
| Is it prompt writing? | No. It is gradient-based training of embedding vectors |
| Does it beat prompt engineering? | Only if prompting plus retrieval measurably hit your eval ceiling |
| Does it beat LoRA in 2026? | Rarely on quality. Sometimes on serving cost for many adapters |
| Can you do it on a hosted API? | No. Embedding access is required |
| Should you reach for it first? | No. Prompt first, eval, then escalate |

## 7. The 2026 serving numbers: soft prompt vs LoRA 📊

The freshest evidence is not about accuracy, it is about **inference economics** - and it is the best argument prompt tuning has left. A 2026 infrastructure study compared a quality-matched pair (both adapters distilled from the same teacher, both recovering the same gain) on Qwen3-8B with LiveCodeBench traffic:

| Metric | Base (no adapter) | Soft prompt (256 tokens) | Unmerged LoRA (rank 1) |
|---|---|---|---|
| Median time per output token | 6.1 ms | 6.1 ms | 16.8 ms |
| Peak throughput | 3,492 tok/s | 3,481 tok/s (-0.3%) | 2,443 tok/s (-30%) |
| Time to first token (single request) | 20 ms | 39 ms | (adapter kernels, see TPOT) |
| Extra KV per cached tenant prefix | no | 36 MiB | no |
| Prefix-cache hit rate (shared system prompt) | no | 63.5% | 47.1% |
| Behavior from 8 to 256 GPU-resident tenants | no | Flat | Flat, but at the slower per-token cost |

Read the shape of it: **the soft prompt decodes at bare-backbone speed**, because at decode time it *is* the bare backbone plus some extra prompt positions. Its entire price is paid in **prefill and KV memory** (39 ms TTFT vs 20, 36 MiB per tenant). Unmerged LoRA pays on **every decode step** - roughly 2x the per-token cost here - and mixes worse with prefix caching, because a LoRA changes every layer's keys and values so cached prefixes cannot be shared across adapters.

The trade in one line: soft prompts rent space in the context window, LoRA rents time in the decode loop. With 8 to 256 tenants both scale flat, so the single-adapter gap carries over.

Caveats baked into the study itself: one backbone, one task, one GPU type, two seeds, and the multi-tenant runs replicate one adapter under many names. Directional, not gospel.

## 8. The escalation ladder: when to actually use it 🪜

Both HF's PEFT docs and the 2026 surveys describe the same ladder. Do not skip rungs:

| Rung | Move | Use when |
|---|---|---|
| 1 | **Prompt engineering** (hard prompts, few-shot, retrieval) | Always first. Most tasks die here, happily |
| 2 | **Prompt optimization** (DSPy, GEPA, search over text) | Prompting works but the wording is fragile and you want it found mechanically |
| 3 | **Prompt tuning / prefix / P-tuning v2** | Self-hosted frozen model, embedding access, many narrow task variants, few hundred labeled examples each, and rung 1 measurably hit its ceiling |
| 4 | **LoRA / QLoRA** | Single task (or few), quality first, still want PEFT economics. The 2026 default |
| 5 | **Full fine-tuning** | Novel behavior far from the pretraining distribution, or regulated mergeable-weights requirements. Prove rungs 1 to 4 failed first |

Prompt tuning is the right call on rung 3 **only** when all of these hold:

1. You self-host open weights (Qwen3, Llama 4, Mistral-class).
2. A clearly defined narrow task with a labeled dataset of at least a few hundred examples.
3. Prompt engineering plus retrieval hit a **measured** ceiling on your eval set.
4. You need many task adapters in one deployment, not one good fine-tuned copy.
5. Inference simplicity matters (no adapter matmuls in the decode loop).

**The eval gate is the same everywhere**: train a soft prompt *and* a LoRA on one sample task, score both against the hand-written prompt baseline on held-out examples (average **and** worst decile), and keep the winner. An adapter that cannot beat prompting is a training bill with extra steps.

## 9. Applied to your stack 🎯

Your day-to-day is Hermes Agent plus Claude Code over hosted QwenCloud models (`qwen3.8-flash`, `qwen3.8-max`, `deepseek-v4-pro`) via the DASHSCOPE API. The honest verdict:

1. **On the hosted path, prompt tuning is unavailable to you, full stop.** API models expose no embedding layer. This is not a limitation to work around; it is a boundary that makes the decision for you. Your levers stay prompt engineering, retrieval, and the harness work in [[15_harness-maxxing-2026]].
2. **The homelab is where this note could become real.** Self-hosted open weights (llama.cpp or vLLM on your server) give you embedding access and make rung 3 reachable. If you ever want many small task variants - the teaching vault's TH/EN explanations, per-audience styles - a soft prompt per variant is the textbook multi-tenant shape from section 7.
3. **If you go there, the order is fixed**: build the eval set first (move 0 of [[15_harness-maxxing-2026]]), baseline against prompting, then train a soft prompt and a LoRA on one sample task and let the held-out scores decide. The method is cheap; the discipline is the deliverable.
4. **What to take from this note today**: the vocabulary correction. When a vendor or a colleague says "prompt tuning", check whether gradients were involved before you update your mental model.

## 10. Skeptic's corner ⚠️

- **"Matches full fine-tuning" is a 2021 result on T5 models**, mostly NLU-shaped tasks, at 10B+. The independent reproduction base is far thinner than LoRA's. Do not design a production system on the headline alone.
- **The niche is narrow and shrinking from both sides.** Frontend teams never had embedding access; backend teams have LoRA with hot-swap serving on every major engine. Prompt tuning survives where per-adapter serving cost dominates - a real but small population.
- **Soft prompts are un-debuggable vectors.** A bad sentence in a text prompt you can find and fix. A bad soft prompt you can only detect with evals on production traffic. If you cannot afford continuous evaluators, do not adopt soft prompts.
- **Training instability is a property, not an accident.** Tiny parameter counts concentrate gradients. The init-from-text trick, lower learning rates, and warmup are load-bearing, and the hyperparameters are task-specific.
- **The name collision wastes real meeting time.** "We tuned the prompt" and "we trained a soft prompt" are different work with different prerequisites. Section 1 exists because this confusion is the most common failure mode of the whole topic.
- **Section 7's numbers are one study.** One backbone, one task, one GPU type. The direction (decode free, prefill and KV expensive) is structural and trustworthy; the exact percentages are not.
