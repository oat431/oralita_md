# Deerngo Bot — YouTube API OAuth Setup

> A beginner-friendly setup guide for the Deer_NGO channel owner/client.
>
> **Purpose:** Give Deerngo Bot permission to read recent YouTube subscribers so the backend can capture subscribers even when the streamer is not live.

## What This Enables

The subscriber feature has two paths:

| When | Source | Result |
|------|--------|--------|
| During a live stream | streamer.bot | Real-time subscriber event sent to the Go backend |
| Outside live hours | YouTube Data API polling | Backend checks for recent subscribers every 15 minutes |

This note covers the second path: **YouTube Data API access**.

---

## Important: API Key vs OAuth

A normal Google API key is **not enough** to read the channel's subscriber feed.

The backend needs **OAuth 2.0 authorization from the owner/manager of the Deer_NGO YouTube channel**. OAuth allows the backend to act on behalf of that authorized channel account.

The requested permission should be read-only:

```text
https://www.googleapis.com/auth/youtube.readonly
```

Do not share credentials in chat, email, GitHub issues, screenshots, or source code.

---

## What We Need

| Requirement | What it means | Who normally handles it |
|-------------|---------------|-------------------------|
| **1. Google Cloud project** | A container for Google API configuration and quotas | Dev or client |
| **2. YouTube Data API v3 enabled** | Turns on the YouTube API for that project | Dev |
| **3. OAuth client ID and client secret** | Identifies the Deerngo application to Google | Dev |
| **4. Channel-owner consent** | The owner/manager authorizes access to the Deer_NGO channel | Client |
| **5. Refresh token** | Long-lived credential used to obtain short-lived access tokens | Generated by Dev's OAuth setup flow |
| **6. `YOUTUBE_CHANNEL_ID`** | The channel's stable ID, usually beginning with `UC` | Client or Dev |

The client should not need to write code. Dev should provide a one-time OAuth setup command or local authorization page.

## Before Starting

Confirm these items:

- [ ] You can sign in to the Google account that owns or manages the **@Deer_NGO** YouTube channel.
- [ ] Dev has prepared the OAuth bootstrap flow or told you exactly which authorization URL to open.
- [ ] You know where the generated credentials will be stored securely.
- [ ] You will not paste the refresh token or client secret into chat or GitHub.

> **Do not use a Google service account.** The YouTube Data API does not support the service-account flow for this channel access scenario.

## Step 1 — Create or Select a Google Cloud Project

1. Open the [Google Cloud Console](https://console.cloud.google.com/).
2. Sign in with the Google account agreed with Dev.
3. At the top of the page, open the project selector.
4. Either select an existing project for Deerngo Bot or choose **New Project**.
5. Give it a recognizable name, for example:

```text
Deerngo Bot YouTube Integration
```

6. Record the project name or project ID for Dev.

> Keep this project separate from unrelated production projects unless the owner intentionally wants to share quotas and credentials.

---

## Step 2 — Enable YouTube Data API v3

1. Open **APIs & Services → Library**.
2. Search for **YouTube Data API v3**.
3. Open the official Google API entry.
4. Click **Enable**.
5. Confirm that the correct Google Cloud project is selected.

Direct link: [YouTube Data API v3 in Google Cloud](https://console.cloud.google.com/apis/library/youtube.googleapis.com)

---

## Step 3 — Configure the OAuth Consent Screen

Google's current console may call this **Google Auth Platform**, **OAuth consent screen**, or **Branding** depending on the console view.

1. Open **Google Auth Platform / OAuth consent screen**.
2. Configure the application information:
   - App name: `Deerngo Bot`
   - User support email: an email monitored by the owner
   - Developer contact email: the project contact
3. Choose the correct audience:
   - A personal Google account normally uses **External**.
   - A Google Workspace organization may use **Internal**, if appropriate.
4. Add the YouTube scope requested by Dev:

```text
https://www.googleapis.com/auth/youtube.readonly
```

5. If the app is in **Testing** status, add the channel owner's Google account as a test user.
6. Save the configuration.

### Long-Term Service Warning

For an always-on backend, do not casually leave an External OAuth app in **Testing**. Google documents that refresh tokens issued to an External app in Testing can expire after 7 days when non-basic scopes are requested.

For a long-running service, Dev and the owner should complete the appropriate publishing/production configuration. Google may require additional consent-screen or verification steps depending on the account, scopes, and current Google policy.

---

## Step 4 — Create OAuth Client Credentials

1. Open **APIs & Services → Credentials** or the OAuth client section in Google Auth Platform.
2. Choose **Create OAuth client**.
3. Use the client type specified by Dev:
   - **Desktop application** for a one-time local authorization helper, or
   - **Web application** if Dev implemented an OAuth callback endpoint.
4. If Google asks for a redirect URI, enter **exactly** the URI supplied by Dev.
5. Download the client credentials JSON if Google provides it.
6. Store it in a secure location outside Git repositories.

Direct link: [Google Cloud Credentials](https://console.cloud.google.com/apis/credentials)

### Do Not Commit This File

Never commit any of the following:

```text
client_secret*.json
.env
.env.local
refresh-token files
OAuth token dumps
```

---

## Step 5 — Complete Channel-Owner Consent

Dev should now start the OAuth bootstrap flow.

1. Open the authorization URL or local page provided by Dev.
2. Sign in with the Google account that owns/manages **@Deer_NGO**.
3. Check the application name before continuing.
4. Confirm that the requested permission is read-only YouTube access.
5. Approve the request.
6. Allow Dev's bootstrap flow to finish and exchange the authorization code.

If Google shows a testing/unverified warning, stop and confirm with Dev that the URL and application are the expected Deerngo application. Do not approve an unfamiliar application.

---

## Step 6 — Store the Refresh Token Securely

The OAuth flow returns a refresh token. The refresh token lets the backend obtain new short-lived access tokens without asking the client to sign in every hour.

For this project:

- The refresh token must never be committed to Git.
- The refresh token must never appear in application logs.
- The token should be stored in the secure deployment environment or the project's protected `oauth_tokens` database record, according to Dev's implementation.
- Only the Deerngo backend should be able to read it.

The database design stores the YouTube refresh token in the `oauth_tokens` table together with:

```text
provider = youtube
youtube_channel_id = UC...
refresh_token = <secret>
```

Send the token to Dev only through the secure method agreed for the project, such as a password manager or protected secret store.

---

## Step 7 — Find `YOUTUBE_CHANNEL_ID`

The channel ID is **not** the same thing as the public handle `@Deer_NGO`.

### Recommended Method: YouTube Studio

1. Open [YouTube Studio](https://studio.youtube.com/).
2. Select the Deer_NGO channel.
3. Open **Settings**.
4. Open **Channel → Advanced settings**.
5. Find and copy the **YouTube Channel ID**.

It normally looks like:

```text
UCxxxxxxxxxxxxxxxxxxxxxx
```

Send only the channel ID to Dev. It is not a secret.

---

## Step 8 — Give Dev the Non-Secret Configuration

The current backend configuration already defines `YOUTUBE_CHANNEL_ID`. Dev will confirm the exact names for the OAuth values before implementation.

Suggested configuration shape:

```text
YOUTUBE_CHANNEL_ID=UCxxxxxxxxxxxxxxxxxxxxxx
YOUTUBE_OAUTH_CLIENT_ID=<secure configuration>
YOUTUBE_OAUTH_CLIENT_SECRET=<secure secret>
YOUTUBE_POLL_INTERVAL=15m
```

The refresh token may be stored in the protected `oauth_tokens` database row instead of an environment variable, depending on the implementation.

> The current repository `.env.example` exposes `YOUTUBE_CHANNEL_ID` but not all OAuth bootstrap variables yet. Dev must add the final configuration names and setup instructions before closing the YouTube polling issue.

## Step 9 — Dev Verification Checklist

The client does not need to run these alone. Dev should verify:

- [ ] The OAuth account is the Deer_NGO channel owner/manager.
- [ ] The refresh token can obtain a new access token.
- [ ] The backend calls the authorized YouTube subscriber endpoint.
- [ ] The polling interval defaults to 15 minutes and is configurable in tests.
- [ ] New records use `source = youtube_api`.
- [ ] Duplicate subscribers are upserted without duplicates.
- [ ] The earliest `subscribed_at` timestamp is preserved.
- [ ] A `401 Unauthorized` is logged safely and alerts the operator for reauthorization.
- [ ] A `403 quotaExceeded` is handled without a tight retry loop.
- [ ] Tokens and secrets do not appear in logs or error responses.
- [ ] A real or approved test subscriber appears in PostgreSQL.

Example database verification by Dev:

```sql
SELECT youtube_handle, display_name, subscribed_at, source
FROM subscribers
WHERE source = 'youtube_api'
ORDER BY subscribed_at DESC;
```

## Platform Limitations to Understand

The YouTube API is not a guaranteed event stream for every possible subscriber.

- Google documents that the recent-subscriber result may be limited.
- Some viewers may have private subscription activity and may not be visible to the channel owner through the API.
- The channel's subscriber visibility and YouTube API behavior must be validated during testing.

Therefore, the goal is **best available 24/7 capture**, with streamer.bot providing real-time live-stream coverage and YouTube polling recovering subscribers outside live hours. If testing shows that YouTube does not expose a class of subscribers, Dev and PO must document that limitation rather than claiming the API can capture them.

## Troubleshooting

| Symptom | Likely Cause | Action |
|---------|--------------|--------|
| `access_denied` | Wrong Google account or account not added as a test user | Sign in with the channel-owner account; ask Dev to check OAuth audience/test users |
| `redirect_uri_mismatch` | Redirect URI differs from the OAuth client configuration | Use the exact redirect URI supplied by Dev |
| `invalid_client` | Wrong client ID/secret or wrong credentials file | Recheck the selected Google Cloud project and secure client file |
| `invalid_grant` | Refresh token revoked, expired, or generated for another client | Reauthorize and securely replace the stored refresh token |
| `401 Unauthorized` | Access token cannot be refreshed or authorization was revoked | Dev must alert the operator and run OAuth consent again |
| `403 quotaExceeded` | API quota was exhausted | Check Google Cloud quota and verify the scheduler is not polling too frequently |
| Empty subscriber result | No exposed recent subscribers, private subscriptions, wrong channel, or invalid authorization | Verify channel ID/account and run a controlled test; ask Dev to inspect API response |
| Refresh token stops working after a few days | OAuth app remains in External/Testing status | Review publishing/production configuration with Dev and Google requirements |
